# PRISMA — canonical method

Version: 0.1.0-rc.1 · Status: unpublished release candidate · Language: English

## First use

Give this file to an AI that can actually read it. If live retrieval is unavailable, attach the complete verified method package. Neither act installs a tool or grants authority. Say:

> Apply PRISMA to the following question. Identify the governing source and what was actually read. Choose the smallest useful mode and roster, preserve uncertainty and disagreement, and return candidates without changing the source unless I authorize the specific mutation.

Include the project, task, relevant documents, desired intensity, audience/destination and boundaries. For a simple task, use a direct answer. If a source is missing, request it or offer a bounded functional perspective. Never silently fill the gap. See [synthetic examples](examples/README.md).

## Mother law

Adapt the form, roster, questions and intensity to the field; preserve the authority of facts, permissions, source provenance, canon and human decisions. Representation does not grant evidential or operational authority. A named perspective is not inherently more useful than an unnamed one.

## Input and resolution

Resolve the governing jurisdiction, current source, concrete task, representation class, actual evidence and freshness, knowledge/time boundary, relevant sensitivities, audience and intended output, activation mandate, persistence authorization and available tools. Source availability and source authority are distinct. No automatic writeback, public transfer, consent, permission or canonicalization follows from access.

Classify each perspective: public/historical person, fictional character, constructed archetype, functional chair, or consented personal mirror. For private persons, avoid identifying impersonation and undocumented inner states; use functional or hypothetical reception alternatives. For public figures, distinguish documented public claims from interpretation. Do not invent statements, citations, private intentions, diagnoses or testimony. For fictional characters, use the author's current canon and the character's permitted knowledge at the stated time. A proposed change is not canon. Mirror requires explicit consent and an appropriate governing corpus, not inferred consent.

## Modes

| Mode | Function | Required boundary |
|---|---|---|
| Lens | Reconstruct relevant documented reasoning and arguments | Sources actually inspected; no fabricated quote; missing evidence means functional fallback or insufficiency |
| Mask | Creative dramatization explicitly requested | Label fictional simulation before speech; never attribute it as actual speech; private identifying impersonation excluded |
| Table | Compare distinct bounded perspectives | Mandates, independent criteria where possible, real differences, no fake quorum or independent agent claim |
| Mirror | Bounded consented self-representation | Explicit opt-in, suitable source and source owner; not the living person or new testimony |
| Counterproof | Expose failure conditions, objections and competing explanations | Test real assumptions; do not fabricate dissent or evidence |
| World | Explore fictional characters, institutions, worlds | Canon, chronology, limited knowledge and authorial gates; candidate only |
| Reception | Explore possible audience readings | Hypothesis, not prediction guarantee or access to someone's thoughts |

Modes are composable but not interchangeable. Use the strongest applicable boundary. A Table does not inherently simulate personal identity; a Mask does not constitute independent deliberation. A named public Lens may be useful without mimicking a voice. A functional chair should not be passed off as a specific person.

## Operational pipeline

1. **Preflight:** resolve task, authorization, jurisdiction, actual runtime capabilities and the minimum necessary sources. If scope or permissions are missing, limit or block the unsafe branch.
2. **Decompose:** separate source facts, documented positions, interpretation, hypotheses, fictional alternatives and unavailable evidence. Record source locators, versions and relevant time bounds.
3. **Constitute:** make temporary profile cards only for useful perspectives: identity/class, mandate, evidence, permitted knowledge, priorities, reasoning method, uncertainty and limits. Use 1–5 as a practical default; expand only for meaningful coverage. No ornamental roster.
4. **Adapt:** select different modes, questions, depth and presentation for each domain. Preserve invariants under a domain change; never import someone else's canon or private corpus.
5. **Represent:** answer each question within the profile's knowledge and mandate. Label epistemic status on contributions; label dramatized speech up front. A documented claim needs a locator; an interpretation needs grounds; a hypothesis needs uncertainty; a fictional statement needs a fiction label.
6. **Confront:** compare what each perspective notices, misses and disagrees with. Ask for a counterexample or failure condition where useful. Preserve actual disagreement; don't fabricate conflict or consensus. A single model's multiple voices do not prove multiple agents, independence, or external review.
7. **Synthesize:** distinguish convergences, disagreements, candidate improvements, limitations and unresolved questions. Keep the user's project sovereignty. No unsupported consensus or invented third-party approval.
8. **Return and persist:** default READ_ONLY. For a separately authorized mutation, verify the smallest sovereign destination, preview the eligible delta, apply with provenance, reread actual external state, and report accepted only after readback. Missing readback means pending_unverified. Do not publish automatically or act outside the runtime.

## Evidence labels

`documentado` (documented), `interpretação_sustentada` (supported interpretation), `hipótese` (hypothesis), `ficção_rotulada` (labeled fiction), `não_verificado` (unverified), `não_representável_com_lastro` (insufficient grounds). English machine aliases: `documented`, `supported_interpretation`, `hypothesis`, `labeled_fiction`, `unverified`, `insufficient_basis`. These labels describe the claim, not the person. Do not promote one without evidence. Quotes require verified verbatim text and correct attribution; simulated text is never a quote.

## Return contract

Return question and jurisdiction, real sources inspected and missing, mode and class, profile mandates and boundaries, contributions with labels, disagreement and counterproof, actionable candidate or no useful delta, decisions reserved for the user, and persistence/readback status. Keep source facts separate from generated content. For high-risk fields use generic educational/functional scenarios only within authorization; never convert a hypothetical into a medical record, legal proof, diagnosis or real testimony. See [adapter contract](ADAPTER_CONTRACT.md), [epistemic contract](docs/EPISTEMIC_AND_SIMULATION_CONTRACT.md), [modes](docs/REPRESENTATION_MODES.md) and [public boundary](PUBLIC_BOUNDARY.md).

## Failure and fallback

No internet: use available local source, identify limits; an unsourced named Lens is unavailable. No Moon Source: retain the standalone input, authority and receipt rules above. No separate agents: use transparent one-model perspectives. No consent: no Mirror. No source/canon: no assertion, only explicitly bounded generic hypothetical. No authorization: no mutation. No readback: pending. In simple tasks or no meaningful contrast, answer directly. Lack of a useful simulation is a valid outcome.

The optional [reference gate](reference/gate.py) only checks declared preconditions; it does not validate human consent, source authenticity, medical facts, model outputs or actual remote mutation. Operator verification remains necessary.
